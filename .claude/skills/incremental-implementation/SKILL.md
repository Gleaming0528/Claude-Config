# 递增实现

## 概述

以薄垂直切片构建功能——实现一小块、测试、验证、然后扩展。避免一次性实现整个功能。每个增量结束后系统必须处于可工作、可测试的状态。

## 适用场景

- 实现任何多文件改动
- 从任务分解列表构建新功能
- 重构现有代码
- 任何你想一次写超过 ~100 行代码的时候

**不适用：** 单文件、单函数、范围已经最小化的改动。

## 增量循环

```
┌──────────────────────────────────────┐
│                                      │
│   实现 ──→ 测试 ──→ 验证 ──┐        │
│    ▲                       │        │
│    └───── 提交 ◄───────────┘        │
│           │                         │
│           ▼                         │
│       下一个切片                     │
│                                      │
└──────────────────────────────────────┘
```

每个切片：

1. **实现** 最小的完整功能片段
2. **测试** — 跑测试套件（或先写测试，参考 `test-driven-development`）
3. **验证** — 确认切片工作正常（测试通过、构建成功）
4. **提交** — 描述性 commit message（参考 `hpc-commit`）
5. **推进** — 进入下一个切片

## 切片策略

### 垂直切片（首选）

一次构建一条完整的穿透路径：

```
切片 1: 创建推理服务（DB + API + 基础 UI）
    → 测试通过，用户可以通过 UI 创建推理服务

切片 2: 列表推理服务（查询 + API + UI）
    → 测试通过，用户可以看到服务列表

切片 3: 更新推理服务（更新 + API + UI）
    → 测试通过，用户可以修改服务配置

切片 4: 删除推理服务（删除 + API + UI + 确认）
    → 测试通过，完整 CRUD 完成
```

### 契约先行切片

后端和前端需要并行开发时：

```
切片 0: 定义 API 契约（Go types / OpenAPI spec）
切片 1a: 后端按契约实现 + API 测试
切片 1b: 前端按 mock 数据实现
切片 2: 集成联调 + 端到端测试
```

### 风险先行切片

先攻克最不确定的部分：

```
切片 1: 验证 K8s CRD 能正确创建 Pod（最高风险）
切片 2: 在验证过的 CRD 基础上构建控制器逻辑
切片 3: 添加状态同步和错误恢复
```

如果切片 1 失败，在投入切片 2/3 之前就发现了。

## 实现规则

### Rule 0: 简单优先

写代码前问："最简单的可行方案是什么？"

```
检查清单：
✗ 为一个通知场景写通用 EventBus + 中间件管道
✓ 直接函数调用

✗ 为两个相似组件写抽象工厂
✓ 两个直接的组件 + 共享工具函数

✗ 为三个表单写配置驱动的表单生成器
✓ 三个表单组件
```

三行相似代码好过一个过早抽象。先实现正确的朴素版本，测试通过后再优化。

### Rule 1: 一次只做一件事

每个增量只改一个逻辑单元。不要混合关注点：

**错误：** 一个 commit 添加新组件 + 重构旧组件 + 更新构建配置

**正确：** 三个独立的 commit

### Rule 2: 保持可编译

每个增量结束后，项目必须能构建、现有测试必须通过。不要让代码库在切片之间处于破碎状态。

```bash
# Go 项目每个切片后验证
go build ./... && go test ./...

# 前端项目每个切片后验证
npx tsc --noEmit && npx vite build
```

### Rule 3: 范围纪律

只改任务要求的东西。

**不要：**
- "顺手"清理不相关代码
- 重构你只是在读的文件的 import
- 删除你不完全理解的注释
- 因为"看起来有用"就加不在需求里的功能

```
注意到但不动：
- src/utils/format.go 有未使用的函数（和本任务无关）
- auth 中间件的错误消息可以改进（另开任务）
→ 要我为这些创建单独的任务吗？
```

### Rule 4: 安全默认值

新代码应默认为安全、保守的行为：

```go
type CreateOptions struct {
    Notify   bool // 默认 false，需要时显式 opt-in
    DryRun   bool // 默认 false
}
```

### Rule 5: 可回滚

每个增量应独立可回退：

- 添加性变更（新文件、新函数）容易回退
- 对现有代码的修改应最小化、聚焦
- 数据库迁移应有对应的回滚迁移
- 避免在同一个 commit 中删除又替换

## 反合理化

| 借口 | 现实 |
|------|------|
| "最后一起测" | Bug 会叠加。切片 1 的 bug 让切片 2-5 全部错误。每个切片都测。 |
| "一次做完更快" | 一次做完**感觉**更快，直到出了问题，你在 500 行改动里找不到是哪行导致的。 |
| "这些改动太小不值得分开提交" | 小 commit 几乎零成本。大 commit 隐藏 bug、让回滚变成噩梦。 |
| "这个重构很小，顺带做了" | 重构和功能混在一起，两者都更难 review 和调试。分开。 |
| "先把功能做完再说，feature flag 之后加" | 功能没完成就不应该对用户可见。现在就加 flag。 |
| "直接写完整方案，不需要先写朴素版本" | 朴素版本暴露你对需求的理解是否正确。完整方案建立在错误理解上 = 全部返工。 |

## Red Flags

- 超过 100 行代码没有跑测试
- 单个增量中混入多个不相关改动
- "让我顺便也加上这个"——范围蔓延
- 跳过测试/验证步骤以加快速度
- 增量之间构建或测试处于破碎状态
- 大量未提交的改动堆积
- 在第三个使用场景出现之前就创建抽象
- 改动了任务范围之外的文件

## 验证清单

完成一个任务的所有切片后确认：

- [ ] 每个增量都单独测试并提交
- [ ] 全量测试通过
- [ ] 构建无错误
- [ ] 功能端到端按需求工作
- [ ] 无未提交的改动残留
- [ ] 没有范围之外的改动混入
